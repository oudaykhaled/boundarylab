# Controlled measurement

[experiment-v1.json](experiment-v1.json) freezes the initial physical-device design before confirmatory measurements. The Samsung SM-A336B/API 36 is available for scoped tests; availability alone is not a completed campaign. M01 remains incomplete until the ten-pair pilot, baseline parity and final calibration are recorded. M02–M04 remain open until their actual measurements exist. No synthetic timing is presented as hardware evidence.

The no-work shell measures launch/first frame with identical UI but no hashing. In-process and broker variants must call the same native 64 KiB positional reader and digest implementation. Flutter's in-process baseline still crosses the authored native channel; Dart hashing is not a substitute. Pin release optimization and compilation/profile state, all client/broker APK hashes, source commit, Android build fingerprint, refresh rate and power/charging state. Record only non-identifying properties. Frameworks are separate comparisons; their absolute timings need not be ranked.

Run `python3 benchmarks/schedule.py --plan benchmarks/experiment-v1.json --output /tmp/boundarylab-schedule.json` to produce deterministic randomized balanced startup blocks. This creates a schedule only and does not run a device or manufacture results. Revision 2, before any measurements, separates 360 no-work launch observations (three sessions × 30 repeats × two frameworks × cold/resident) from 720 planned explicit-interaction observations (also × in-process/broker). Actual applications lazy-bind: a launch makes no broker call and cannot show a startup IPC delta. Assert no bind/session/hash on default launch. Measure explicit prepare/connect→READY and submit→terminal/UI-visible latency separately, recording fresh/reused connection state and never pooling those states. The ten paired pilot trials are separate and excluded from confirmation. Default launches are baseline observations, never a hashing-speed pool. Equal-work in-process interactions remain a future test-build prerequisite; no auto-connect production variant is introduced.

File correctness includes 0, 1 KiB, 1 MiB, 16 MiB and 128 MiB, both 32-file pack sizes and invalid boundary cells. File timing windows use three declared native sizes and the declared Flutter subset; file/storage and generated-byte compute results stay separate. Invalid inputs measure rejection correctness, never hashing throughput. Load uses three sessions × five 60-second windows × concurrency 1/2/4/8 per treatment; a separately calibrated fixed-arrival overload run reports offered/accepted/BUSY/completed outcomes. Three 30-minute memory/churn sessions capture all client plus broker PSS and logical counters. Reserve 12–24 device-hours separately from engineering time; additional provider/device profiles need separate allocation.

Randomize treatments within balanced blocks. Record process cold/resident separately from filesystem cache prewarmed/uncontrolled: process restart does not establish disk coldness. Thermal status above LIGHT (1), battery temperature above 38°C, competing test execution or missing/overrun trace events invalidates the affected trial; preserve it with the exclusion reason. Cool for at most 15 minutes and require two safe samples 30 seconds apart; then mark the cell incomplete if still unsafe. Do not change personal device settings to force a result.

Stage timing uses one documented Android monotonic clock domain and job correlation IDs: launch/first-frame, provider open, FD handoff, admission, queue, read/hash, terminal commit, polling observation and export. Poll delay is not control-RPC latency. FD transfer is not a copy of all attachment bytes over Binder. Overlapping spans are not summed. Missing milestones are unknown, never zero. Compare trace-on/off pilot overhead; collect PSS separately from traced timing. Desktop RSS and Android PSS are different metrics.

`analyze.py` reads real newline-delimited observations and reports per-session counts, failures, exclusions, medians and p95. It refuses duplicate trial identities, non-finite/negative latency, unknown statuses, nonphysical rows, or successful observations lacking a metric. It never imputes excluded/failed latency. Its pooled data is explicitly descriptive; three sessions do not justify a general phone-population claim or p99. Protected digest/resource counters must return to zero after drain; >10% cancellation-p95 or total-PSS-median regression rejects an improvement proposal even if hashing improves. Pilot calibrates targets; no universal throughput floor is asserted.

Example input schema (values are illustrative, not a measurement):

```json
{"session":1,"trial":1,"framework":"native","treatment":"broker","operation":"generated-sha256-v1","bytes":1024,"process_state":"resident","cache_state":"uncontrolled","metric":"end_to_end_ms","value":null,"status":"excluded","reason":"illustrative only","device_class":"physical"}
```

Run `python3 benchmarks/analyze.py --input raw.jsonl --output analysis.json`; original raw rows remain immutable. Hash and archive raw data, plan, schedule, APKs and report together. Test fixtures under `benchmarks/test_analysis.py` are synthetic validation data only and cannot close physical evidence gates.
