# Delivery replan: FieldPack, real files and honest completion gates

Status: independent proposal, 2026-10-30. No product builds, devices, services or external writes performed. Reviewed the current backlog, architecture, roadmap and issue snapshot. All implementation tickets below remain **planned**, with no execution evidence. Root owns reconciliation, board writes and final status.

## Recommendation and scope correction

Keep BoundaryLab's existing process boundaries and replace generated-work-only acceptance with a small **FieldPack attachment integrity** workflow. An inspector selects authorized local files, assigns safe export names, requests SHA-256 checksums, exports a versioned manifest, and manually supplies corresponding files to a recipient. The macOS CLI verifies an explicitly supplied directory and reports matched, changed, missing and invalid entries. There is no network transfer. Integrity does not establish authorship, authenticity, malware safety or that the source was immutable throughout reading.

First deliver the Python reference and contract as a runnable specification; it is useful immediately but proves neither Android Binder nor Flutter integration. Next complete a native Android file boundary with fault evidence. Then add Flutter and macOS JVM conformance plus measurement. The conditional AOSP implementation is a separate funding/readiness decision, not required to call the core FieldPack MVP complete.

The existing architecture excludes real files and uses descriptor-only generated bytes. Its field contract, lifecycle, resource accounting, evidence policy, demo and requirements matrix must change together. Keep deterministic generated data as controlled performance fixtures, never as the only implemented input. Existing B01–B16 remain umbrellas; retire their old numeric estimates from active rollups when leaf estimates replace them.

The historical 40/120/240-hour targets are **prior hypotheses** for a narrower operation. They should remain in revision history, marked superseded, rather than redefined to make the expanded scope appear on time.

## Product boundary that controls delivery risk

MVP accepts a bounded set of individually selected files, with one open descriptor per active transfer and strict limits on file count, work bytes, metadata and retained results. Freeze proposed limits in the contract ticket: 16 files per pack, 128 MiB per file, 512 MiB total observed bytes, 64 KiB work buffer, one worker, bounded admission and 1 MiB metadata/result retention. A size advertised by a provider is a hint; enforce observed-byte limits too. Descriptor caps include queued/active/rejected paths, not merely worker memory.

For the first Android implementation, admit only file descriptors whose supported type and seek behavior are established by the adapter. Reject pipes/nonseekable or unsupported provider representations with a typed `UNSUPPORTED_SOURCE` result and close them. This deliberately narrows provider coverage and avoids pretending arbitrary provider streams have bounded cancellation. If nonseekable support becomes required, create a separately estimated ticket for interruption, pipe reads and provider failures; do not hide it in the FD ticket.

Export is a separate user action after all selected entries succeed. Partial results can be inspected but cannot be labeled a complete pack. Manifest paths are logical recipient-relative names, not Android URIs, original absolute paths or user identifiers. Use a conservative flat filename policy initially; reject separators, dot/dot-dot, duplicate names, case-fold collisions and unsupported Unicode variants rather than promise cross-filesystem normalization. Supporting nested paths and sophisticated rename UX is deferred. Explain that the user must supply files using those logical names. Android output uses user-selected destination; failed/cancelled writes are errors and may leave a partial provider document, never a claimed atomic export.

Cancellation is cooperative; publish no hard latency guarantee for arbitrary storage. On a blocked/failed provider operation, report the actual state and limitations. Metadata checks may detect some mutation but cannot prove a snapshot. A successful digest means the observed byte stream hashed successfully. Use controlled fixtures to demonstrate recipient changed/missing detection. Same-publisher trust, volatile jobs, explicit resubmission and fresh epochs remain mandatory.

## Definition of ready and completion

A leaf is ready only when: inputs/outputs and negative outcomes are named; predecessor artifacts are available at known revisions; one owner role is assigned; test fixtures are project-owned; target resources and existing access are identified; estimate includes tests/docs; no unresolved safety-critical contract decision remains. Design/scaffolding can start before integration predecessors finish, but does not count as acceptance.

A resource being installed is not readiness. Android requires an authorized test target, working SDK/JDK/Gradle combination, separate signing identities and provider-test strategy. Flutter requires native plugin build capability, not only Dart checks. macOS requires a supported existing JDK and a working Unix-socket spike. Measurement additionally requires a physical phone and stable conditions. Record missing resources as blockers; do not purchase, flash or provision outside later authorization.

Done means implementation, appropriate tests, review record and revision-linked evidence satisfy that leaf's criteria. Build, device verification, release and publication are distinct statuses. No board checkbox converts illustrative reference output into native evidence.

## Proposed implementation-sized tickets

The following compact format supplies key, parent, type/phase/priority, owner, dependencies and hours. Each paragraph supplies user value/scope, exact acceptance, verification/evidence and risks. All ranges are focused person-hours including ordinary fixes, tests and documentation. Root can map these proposed D keys to final global issue keys without duplicating scope.

### D01 — Establish core target readiness

**B01; spike; preparation; P0; build/platform engineer; depends: none; 4–8h; R01,R03,R11,R15,R19.** Prove Android sample install, separate-signature test configuration, Flutter native build path and macOS two-process socket sample on allocated existing targets. Record versions, commands, failures and device class with identifiers redacted. Missing physical measurement hardware blocks measurement only; absent Linux resources block AOSP only. Acceptance requires executed smoke receipts, not binary discovery. Risk: toolchain repair exceeds estimate; stop and re-estimate the affected platform rather than moving unrelated tasks to blocked.

### D02 — Freeze FieldPack schema, ownership and error contract

**B01; contract; preparation; P0; architect; depends: none; 8–14h; R01,R05,R07,R10,R16.** Specify schema/version, SHA-256 and byte-count representation, logical names, all caps, descriptor lifecycle, incomplete export, epoch loss and mutation caveat. Golden cases include empty file, binary file, duplicate names, bad hash syntax, future major version, oversize entries and traversal names. Acceptance: every input has an error/result, no URI/path privacy leak and no ambiguity between complete and partial manifest. Evidence: versioned schema, normative fixtures and decision record. Risk: unnoticed semantic mismatch across JSON number implementations; choose bounded integral byte counts consistently.

### D03 — Runnable Python reference create/verify and tests

**New FieldPack reference epic; implementation; reference; P0; Python engineer; depends: D02; 8–14h; R09,R10,R11,R17.** Stream actual user-specified files and verify manifest against an explicit directory; no network or hidden fixture substitution. Reject invalid schema/paths/symlinks under the declared support policy, distinguish missing/changed from malformed inputs with documented exits, bound bytes and entries, and never print absolute input paths in evidence. Tests mutate one byte, remove one file, use empty/binary input, duplicate entries and attempt traversal. Evidence: test output, commands and project-owned fixture results. Static path checks do not defeat a malicious concurrent local filesystem actor; disclose that threat limit. Root may implement this bounded task during the present planning request; update only its actual completion state afterward.

### D04 — Bounded core with file-stream operation and manifest model

**B02; implementation; native foundation; P0; Kotlin engineer; depends: D02; 12–20h; R05,R07,R08,R10.** Implement transport-independent state/admission and stream hashing using explicit source interfaces. Enforce observed-byte limits, result TTL/byte ceilings and per-owner fairness. Tests cover empty/exact-limit/limit-plus-one, read failure, queue saturation, deadline-before-start, completion/cancel race and expired results. Evidence: deterministic test report and shared golden vectors. No Android imports or whole-file buffering. Risk: queue retains sources; cap resource ownership explicitly and close rejected/evicted work.

### D05 — Android provider/descriptor adapter and ownership tests

**B03; implementation; native foundation; P0; Android framework engineer; depends: D01,D02; 10–18h; R05,R07,R14,R16.** Open authorized selected content, classify supported input, transfer descriptor ownership deliberately and close every local/remote owned handle on rejection, cancellation, completion, session death and exceptions. Use a controlled test provider for revoked access, open failure, unknown size, unsupported pipe and mutation. Acceptance: no URI grant assumptions in broker, no reads on Binder/UI ingress, clear errors for unsupported sources, repeated failures return descriptor count to documented baseline tolerance. Evidence: process-specific FD counts and instrumentation records. FD duplication can share file position; tests must not assume independent cursors. Risk: provider behavior differs; claim only tested support.

### D06 — Binder broker and Kotlin SDK integrate file jobs

**B03; implementation; native boundary; P0; Android middleware engineer; depends: D04,D05; 14–24h; R07,R10,R14,R16.** Authorize caller before queuing, handle parcelled descriptors, provide owner-scoped results and epoch-aware SDK. Negative tests: invalid owner, duplicate request with conflicting metadata, broker death after admission, response loss, old epoch and closed descriptor. Completion acceptance: no false success or automatic replay, reconnect is separate from resubmission, all ingress paths bounded. Evidence: real two-process trace, AIDL/SDK tests and closure audit. Risk: reusing same FD for retry changes position; explicit new submission reopens the authorized source.

### D07 — Native FieldPack selection, status and export journey

**B04; implementation; native MVP; P0; Android UI engineer; depends: D06; 10–18h; R09,R14,R18.** Select actual files, review logical names and limits, submit/cancel, show lost/failed entries, then export only a complete manifest to a chosen destination. Verify exported fixtures with D03 once available; acceptance requires actual app recording and exported manifest, not mocks. Evidence uses project-owned files only. Risk: export destination providers may leave partial documents; show failure and recovery guidance.

### D08 — Native FD, owner and failure campaign

**B06; test; native MVP; P0; Android QA engineer; depends: D06; 10–18h; R05,R07,R08,R11,R17.** Instrumentation driver can run independently of native UI completion. ## Estimates and actual dependency graph

D01 and D02 are independent. After D02, reference D03 and core D04 proceed independently; D05 requires target readiness plus contract. D06 joins D04/D05; native UI D07, fault driver D08 and Flutter D09 then branch. Desktop D10 needs core/readiness/contract, **not Flutter**. Compatibility joins clients and faults; measurement does not wait for desktop or release docs. Technology assessment does not wait for the release. These are logical parallel opportunities, not a claim of extra engineers.

The dependency-only critical path is approximately contract/core → Binder → Flutter → measurement → final rehearsal, with the desktop and compatibility branch potentially overtaking it. Actual durations and resource constraints decide which path dominates. With one implementation owner, total focused effort remains the sum; independent branches allow productive switching during toolchain/device blockers, not magically shorter labor. Do not present longest-path labor as a one-engineer completion estimate.

## Conditional AOSP leaf plan

Existing Linux-resource inventory belongs in D01 and can happen early. Platform implementation does not logically depend on desktop or the final core demo, but prioritize core completion for a single owner. AOSP start requires an approved later implementation scope, suitable existing Linux/virtualization resources and a successful unmodified image build/boot. The official requirements materially exceed ordinary app development [S3]. No new cloud purchase or physical flashing is authorized here.

## Board amendments, exclusions and traceability

Replace B01's single omnibus dependency with independently ready contract/resource leaves. B05 should depend on broker contract/integration, not the completed native demo. B06 should start from broker availability, not Flutter completion. B07 should depend on core/contract/macOS readiness, not B05. Split B08 into conformance and CI work; do not make initial workflow drafting wait for faults. B09 may start after relevant Android behavior is stable; desktop is not a logical prerequisite for phone measurement. B11 begins assessment early and finalizes with actual evidence. B12's hardware assessment is early; image feasibility is conditional, not artificially chained to B11. Keep B13–B16 explicitly conditional and outside the core MVP release rollup.

Parent epics carry aggregate estimates computed from unique children only, preferably no independent estimate field. Planning/reference completion does not close an implementation parent. Record prerequisite failures on specific leaves. Board fields should include phase, scope tier, owner, requirement IDs, min/max hours, evidence, readiness and blocker; root alone updates them. Projects access is a root concern and this report does not claim a live board exists.

R01–R12 and R14–R19 have concrete artifact links above. R13 (degree/equivalent practice), R20 (real external partners), R21 (sustained European experience) and R22 (international collaboration) remain **external-evidence-only**. R09 demonstrates implementation and commercial relevance, not real commercial shipment; R18 documents communication but not actual cross-team history. Same-publisher samples do not prove external adoption. No child ticket is assigned a fabricated person, customer or review.

Excluded from the estimates: cloud transfer, nested portable archive format, arbitrary provider streaming, authenticated/signed manifests, persistence/exactly-once, mobile-to-PC sync, desktop GUI, more desktop OSes, external partner onboarding and kernel implementation. A change to those exclusions requires new scoped leaves and estimates, not extra checkboxes on a completed epic.
