# Contract architecture review and actionable amendments

Status: proposed, planning only. Author owns this report only. The reviewed baseline is `planning/backlog.json` and `docs/ARCHITECTURE.md`; none of the native implementation is claimed complete. Scope is FieldPack attachment integrity, retaining BoundaryLab's volatile jobs and ordinary Binder boundary.

## Recommendation

Keep the deterministic generated-byte operation for IPC/scheduling measurement. Add a distinct **hash authorized regular file** capability for FieldPack. Do not reinterpret generated bytes as proof of file handling. Share digest/state/limits policy while isolating descriptor acquisition and filesystem semantics in adapters. A pack is a client-side assembly of up to 32 successful single-file jobs, not an atomic broker batch. Broker death invalidates unfinished handles; no automatic replay. Completed manifests may be explicitly exported, but job state remains volatile.

Freeze these contracts before native implementation. A Python reference can implement manifest create/verify now without claiming Binder, Flutter or JVM integration. Use exact shared vectors later to compare implementations. Its successful file verification demonstrates a useful bounded business operation, not all middleware requirements.

Generated-byte conformance is sufficient for the conditional platform slice; do not route ordinary SDK clients through hidden APIs.

## Frozen proposed constants

| Constant | Value and meaning |
|---|---|
| Protocol | major 1, minor 0; operation IDs `generated-sha256-v1`, `regular-file-sha256-v1` |
| File/operation limit | 134,217,728 bytes (128 MiB) per file/job; zero bytes valid |
| Manifest aggregate | 134,217,728 bytes across at most 32 entries; sum with checked arithmetic |
| Digest buffer | 65,536 bytes, one running worker; never whole-file read/mmap |
| Job descriptor | 4,096 encoded metadata bytes; descriptor handle is separate |
| IPC response/frame | 16,384 bytes maximum including framing payload; reject length before allocation |
| Sessions | 16 global; four outstanding jobs per session |
| Queue | 16 globally queued plus one running; per-session outstanding includes running |
| Terminal retention | 64 entries globally, 60 seconds after terminal commit, 1,048,576 accounted bytes maximum |
| Descriptor retention | At most one input descriptor per admitted file job; maximum 17 broker-owned job descriptors; rejected duplicate inputs close immediately |
| Deadline | Integer relative milliseconds, 1–120,000; default 30,000; checked monotonic deadline at admission |
| Polling | Minimum 250 ms interval per job in SDK; one outstanding status request per handle |
| Manifest encoding | UTF-8, no BOM, at most 16,384 bytes; writer uses LF trailing newline |
| Public alias | 1–64 ASCII bytes, regex `[a-z0-9][a-z0-9._-]{0,63}`; additionally reject `.` and `..` |
| Request/session/job IDs | Random UUIDs in canonical lowercase hyphenated form; server creates sessions/jobs; request IDs caller-created |
| Epoch | Fresh random UUID for every broker/host process incarnation |

Retention ceiling concerns encoded stored metadata/result bytes, not a claim about total JVM heap. Entry limits also bound object overhead; measure actual PSS separately. Results evict oldest terminal commit first; expired IDs return `EXPIRED_OR_UNKNOWN`. Round robin schedules one queued job per session turn; it does not preempt a running file. Deadline stops selection and checks between reads; blocking OS I/O is not a hard real-time guarantee.

## Manifest v1 and verification

Minimal illustrative manifest shape:

```json
{"format":"fieldpack","version":1,"algorithm":"sha256","files":[{"name":"attachment-001.bin","size":0,"sha256":"e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"}]}
```

Required top-level fields are exactly `format`, `version`, `algorithm`, `files`; each entry contains exactly `name`, `size`, `sha256`. Reject unknown fields in v1, duplicate JSON object keys, wrong types (including booleans for integer size/version), negative/oversized sizes, non-finite numbers, duplicate aliases, empty file list, excessive nesting and unsupported versions/algorithms. `sha256` is exactly 64 lowercase hex characters. Entry order is ascending ASCII alias; the writer sorts and verifier requires this order. No timestamps, original filenames, source paths, URIs, owner names or device identifiers are exported. Aliases are deliberately case-normalized and flat to avoid phone/macOS case and path normalization ambiguities. `attachment-001.bin` is an alias, not a claim that the input was a binary document.

An explicitly exported/copied file set uses those aliases. The manifest is useful only if the receiver separately obtains matching files through their own means. Reference `create --root DIR --output MANIFEST [ALIAS ...]` treats explicitly named flat regular files as aliases; it must handle actual caller-provided paths within that selected root, not just fixture constants. Android selects files using a picker, opens a fresh read-only handle, assigns aliases and warns that separately transferred files must retain those aliases. Automatic copying/exporting of source files is a separate UI feature, not an implicit operation of the broker. The manifest output path must be outside the selected input root in the reference implementation to prevent self-inclusion.

Verification checks each manifest alias against the supplied directory and reports `MATCH`, `MISSING`, `SIZE_MISMATCH`, `DIGEST_MISMATCH` or `UNREADABLE_OR_UNSUPPORTED`; overall success requires every entry to match. Extra directory files are ignored and explicitly documented. Reject symlinks, directories, devices, sockets and pipes. Never follow an absolute path, separator, encoded path substitution or `..`; aliases are literal filenames, no percent-decoding. Reference exit codes: 0 all matched/created; 1 integrity mismatch or missing input; 2 invalid manifest/arguments or inaccessible/unsupported input. Diagnostics contain public aliases only by default. A malformed manifest must fail before reading any attachment.

Successful hashing attests the bytes observed through a handle, not a snapshot of a concurrently mutable filesystem. Capture file identity/size/mtime before and after, fail `INPUT_CHANGED` when changed or if actual byte count differs; document that same-size changes with unchanged metadata can escape this heuristic and cause a mixed read. Do not claim adversarial mutation detection, authenticity, signed provenance or malware safety. Reader fixtures can deterministically prove detection of selected mutations, not all races.

## File capability and descriptor ownership

For v1 Android, the client opens the selected URI read-only with `ContentResolver.openFileDescriptor`, never sends a URI for the broker to reopen under its own authority. Use a fresh handle for each submission. Broker accepts only seekable regular descriptors with known nonnegative `fstat` size within the cap. It rejects pipe-backed/nonseekable providers with `UNSUPPORTED_INPUT` before queueing. Some legitimate document providers will therefore be unsupported; surface that limitation plainly. Validate read-only access mode and metadata; close the unmarshalled broker handle on every rejection. The app closes its local handle after synchronous IPC finishes or errors; successful parcel transport creates the broker's independently closeable handle. Broker owns that handle until terminal result/session cleanup. Test close counts in addition to results.

Use positional reads from offset zero (`pread` equivalent), never the shared open-file-description cursor. Duplicating a file descriptor does not guarantee an independent position; this is a required regression case. The digest adapter stops at declared size and checks final size/metadata; it cannot silently hash an arbitrary suffix or accept growth as equivalent. Every read checks byte/deadline/cancel accounting and the worker closes in `finally`. Session death requests cancellation; a running blocking read may delay closure, so no unqualified immediate cleanup promise.

For macOS JVM host, do not invent Unix-domain descriptor passing in standard JDK APIs. Start the host with one explicit input directory and accept only validated flat aliases relative to it. CLI/host operate under the documented same-user trust boundary. Open with no-follow final-component semantics, verify regular file metadata, read through a single opened channel and compare metadata around processing. Pin root identity during startup and reject root replacement detected by revalidation; do not claim race-proof containment against hostile same-user directory replacement. If secure-directory handle operations are unavailable on the tested filesystem/JDK, disclose that remaining race and keep adversarial same-user mutation outside the supported threat model. This desktop path transports file metadata, not file bytes.

Primary references: [Android ContentResolver](https://developer.android.com/reference/android/content/ContentResolver) documents file descriptor opening and provider behavior; [ParcelFileDescriptor](https://developer.android.com/reference/android/os/ParcelFileDescriptor) documents ownership/descriptor APIs; [JDK FileChannel](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/channels/FileChannel.html) distinguishes positional reads from channel position; [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259) informs JSON interoperability. These sources were checked for this report; the stricter limits and schema above are project decisions.

## Job race/state decisions

Admission validates metadata, authorized owner/session, epoch, capacity and descriptor suitability before `ACCEPTED`. Request timeout is not rejection. One serialized state owner arbitrates `ACCEPTED → RUNNING → SUCCEEDED/FAILED/CANCELLED`. A queued cancel commits `CANCELLED` immediately and closes the input. For a running cancel, set `cancelRequested`; the next worker checkpoint submits a cancellation completion. Success and cancel completion race at the state owner: first terminal commit wins, later completion cannot overwrite it. A cancel reply before commit reports `RUNNING(cancelRequested=true)`, not false final cancellation. Deadline follows the same arbitration with `FAILED(DEADLINE_EXCEEDED)`. Session closure makes handles inaccessible immediately but resource cleanup may finish cooperatively.

Deduplication is `(epoch, sessionId, requestId)`. Existing generated operation retains same-input/different-input conflict behavior. **File jobs do not claim equivalent input identity from an FD or path**: reusing a retained file request ID always returns the original job when operation and metadata match, closes any newly passed descriptor and never reads it; differing declared metadata returns `CONFLICT`. Documentation warns that a changed source requires a fresh request ID. No retries after retention expiration without explicit user resubmission. Status by request ID resolves a submission timeout while original epoch/session lives. Broker death returns client `LOST_OR_UNKNOWN`; new epoch rejects old handles with `STALE_EPOCH`. No restoration or implicit replay.

A client assembles a manifest only after every selected file succeeded and all results share the active assembly attempt. Cancellation/failure/loss prevents publishing a success manifest for the pack; show the failed alias. Locally retained successful digest records may be displayed after broker death, but the app must not silently combine them with newly submitted changed files into a supposedly atomic snapshot. A new pack attempt rehashes all inputs, explicitly initiated by the user.
