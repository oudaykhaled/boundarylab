# FieldPack: independent skeptical plan and ticket review

Status: planning recommendations, 2026-10-30. No reference utility, middleware implementation, GitHub issue revision or Projects board is verified by this report. Root owns integration and external writes. This report uses the new brief and existing B01–B16 backlog.

## Recommendation

Proceed with FieldPack as a concrete inspection-attachment integrity workflow. An inspector selects authorized files, computes a manifest, transfers the manifest and attachments by an existing user-controlled route, and a recipient verifies a separately supplied directory. The useful outcome is an explicit list of matching, changed, missing and unsupported attachments. Export/transfer is not phone-to-PC synchronization, and the reference tool does not implement it.

Implement the narrow Python stdlib reference example now, with real file inputs and owned fixtures. Keep Binder, Kotlin/JVM, Flutter, macOS service and AOSP implementation tickets planned. A Python CLI running on a Mac is an executed reference implementation on that host, not completion of B07's two-process JVM transport. Manifest schema and golden vectors can become common conformance artifacts later.

The scope change from deterministic generated bytes to real files materially adds input capabilities, provider behavior, handle ownership, file mutation, privacy and export failure semantics. Revise old estimates; preserve the synthetic operation as a diagnostic fixture if useful, not as a substitute for the promised workflow. Do not simply add “real files” to the original 40-hour milestone acceptance.

## Risks that must become explicit decisions

1. **Integrity is not authenticity.** A modified file and correspondingly modified manifest can agree. Do not call verification proof of origin, authorized inspection, safe content, trusted timestamp or malware clearance. Signatures/key management are outside this increment.
2. **Files are changing resources.** Metadata before/after hashing can detect some mutations but cannot certify an atomic snapshot or exclude adversarial same-size/metadata-preserving edits. State the producer's stable-input precondition and the exact observed-byte semantics. Atomic manifest publication concerns the output file only.
3. **Paths are capability boundaries.** Reject absolute paths, parent components, ambiguous separators, NUL, empty components, duplicate manifest paths and symlinks. A preliminary `resolve()` check alone cannot prevent a later path swap. On supported POSIX systems prefer component-wise descriptor-relative no-follow opening; otherwise scope the reference to trusted, non-concurrently-mutated directory structure and state the limitation.
4. **Document providers are not ordinary files.** Android Storage Access Framework includes cloud-backed providers. A picker selection is not proof of offline/local data. Restrict initial support and describe any provider-mediated I/O honestly. Unknown length, pipes, nonseekability, grant revocation and blocked reads require decisions rather than assuming disk semantics.
5. **Names can be private.** A relative path hides a workstation root but can still expose a person's name or site identifier. Use owned fixture names in evidence; tell users manifests include selected relative names. Never embed content URIs, absolute paths, device serials or contact data in public receipts.
6. **Success is narrow.** Decide whether extra unlisted files are ignored with a warning or produce a nonzero strict-verification result. An empty manifest must not imply an entire inspection was checked. Default to explicit selected-set verification, with entry counts always displayed.

## Detailed implementation-sized ticket recommendations

Keys below are proposed identifiers for the coordinator to reconcile with other reports. Each starts planned with empty evidence. Estimates are child work ranges, not additional amounts on top of B01–B16 umbrella estimates. All priorities are relative to this increment.

### FP10-01 — Freeze manifest and verification result contract

- **Parent/type/phase/priority:** B01; contract; expand; P0.
- **Owner:** architecture/API owner. **Depends on:** none. **Estimate:** 3–5h.
- **User value:** producer and recipient agree exactly what a match establishes.
- **Scope:** version 1 schema with algorithm `sha256`, bounded entry list, portable relative names, integer byte sizes and lowercase hex digests; stable CLI exit/report semantics. Decide duplicate-key handling, extra-file behavior and zero-entry policy.
- **Acceptance:** reject unknown major versions, unsupported algorithms, duplicate object keys and paths, booleans/floats/negative values for byte sizes, malformed digests, oversized manifest and excessive entries. Every result names checked/matched/changed/missing/error counts; unsupported or unreadable input cannot be reported as a successful complete verification. Result language says “matches this manifest.”
- **Verification/evidence:** valid and invalid golden JSON fixtures, a schema decision record, expected exit codes and machine-readable outputs. Fixture digests have an independent known oracle. **Risks:** overpermissive parser and cross-platform name ambiguity. **Requirements:** R01, R03, R10, R11.

### FP10-02 — Stream actual files within a documented filesystem trust boundary

- **Parent/type/phase/priority:** new reference-example epic; implementation; expand; P0.
- **Owner:** reference-tool maintainer. **Depends on:** FP10-01. **Estimate:** 5–9h.
- **User value:** actual user-specified attachments can be checked without loading each whole file.
- **Scope:** stdlib create/verify commands accepting an explicit root and selected relative files; fixed-size reads; manifest-size, count, per-file and aggregate-byte limits; regular-file validation; no recursive unlimited discovery or network code. Choose concrete initial caps in code/docs before acceptance, e.g. 64 KiB chunks, 128 entries and a bounded aggregate workload.
- **Acceptance:** zero-byte and multi-chunk files hash correctly; symlink leaf/intermediate paths, traversal, absolute paths, devices/FIFOs and over-limit inputs fail without reading outside the root. A file crossing its byte cap while read is stopped, not accepted from stale stat size. Unsupported secure-open capabilities produce a documented limitation or explicit rejection, not silently stronger safety claims.
- **Verification/evidence:** tests use temporary owned directories and an external sentinel; assert no outside-root bytes are consumed. Record executed host/Python version and commands without private paths. **Risks:** path races and platform-dependent no-follow support. **Requirements:** R05, R07, R11, R17; reference evidence only, not R14/R15 completion.

### FP10-03 — Publish only complete manifests and define mutation/cancellation failures

- **Parent/type/phase/priority:** reference-example epic; reliability; expand; P0.
- **Owner:** reference-tool maintainer. **Depends on:** FP10-02. **Estimate:** 3–6h.
- **User value:** a failed inspection cannot leave a valid-looking partial manifest.
- **Scope:** validate/hash first, then stage output in the destination directory and atomically replace only on successful completion; explicit overwrite policy and cleanup. Keep output outside the selected input set or reject overlap, including identity aliases where detectable.
- **Acceptance:** input changes detectable by chosen pre/post metadata checks, read errors, interrupted execution, output denial and injected failure before publication leave no newly successful manifest and preserve an existing destination. No statement claims atomic multi-file snapshot or adversarial mutation proof. A rerun is new work. Output publication failure exits nonzero. Ctrl-C behavior is documented and tested in a subprocess where supported.
- **Verification/evidence:** deterministic injected change/error checkpoints, existing-output preservation assertion and clean temporary-output assertion. **Risks:** durability after power loss is different from atomic replacement; do not claim fsync-grade durability without implementing/testing its contract. **Requirements:** R07, R09, R11, R17.

### FP10-04 — Prove the FieldPack workflow with runnable owned fixtures

- **Parent/type/phase/priority:** B10; example/validation; expand; P0.
- **Owner:** developer-experience/QA maintainer. **Depends on:** FP10-01, FP10-02, FP10-03. **Estimate:** 3–5h.
- **User value:** a new reader can create, verify, alter and diagnose a real package.
- **Scope:** small project-authored text/binary fixtures, quickstart, manifest sample and expected outputs. Commands operate on a temporary copy for mutation/missing-file cases, never mutate committed fixtures in place.
- **Acceptance:** clean invocation produces a manifest and verifies it; changed-byte and removed-file invocations fail with distinct diagnostics; root directory can differ between creation and verification; example works for other permitted local inputs; no uploads or private evidence. README explicitly labels native middleware and platform integrations unimplemented.
- **Verification/evidence:** fresh-process command transcript, tool commit, test output and checked sample manifest. Report this ticket complete only after those steps actually run. **Risks:** copy-paste commands overwriting user data; require explicit output and safe temporary workspace. **Requirements:** R09, R11, R18 (documentation only).

### FP10-05 — Specify and implement Android attachment capability ownership

- **Parent/type/phase/priority:** B03; native implementation; expand; P1, future implementation.
- **Owner:** Android middleware engineer. **Depends on:** FP10-01 plus B03's transport/identity child contract. **Estimate:** 8–16h, re-estimate after provider spike.
- **User value:** a future inspector can submit selected attachments without leaking unrestricted storage access.
- **Scope:** declared supported provider/input classes, client-opened read-only descriptor transfer, broker ownership/close semantics on acceptance/rejection/cancel/death, and caller identity captured before dispatch. Do not pass large attachment arrays inside Binder parcels or trust a URI string as authorization.
- **Acceptance:** wrong signing identity and cross-owner handles rejected; descriptor closes on every terminal/rejection path; duplicate/shared descriptor offset behavior investigated and documented; revoked grant, unknown length, nonseekable stream, provider error and blocked read have explicit outcomes. Unsupported input is rejected clearly. Cancelling a blocking provider read cannot be claimed bounded until executed tests support that claim. No automatic job replay after broker death.
- **Verification/evidence:** instrumented provider fixtures, real cross-process receipts, FD-count before/after churn, permission-denial and cancellation-race tests, exact tested API/provider matrix. **Risks:** SAF may invoke cloud providers and descriptor duplicates may share offsets; narrow initial support when needed. **Requirements:** R05, R07, R14, R16, R17.

### FP10-06 — Add FieldPack integration acceptance to both clients and desktop verifier

- **Parent/type/phase/priority:** B04/B05/B07 (split into three implementation children when scheduled); native integrations; expand; P1.
- **Owner:** Android, Flutter and JVM owners respectively. **Depends on:** FP10-01, FP10-05 for Android clients; desktop depends on schema and its B07 socket/core foundations, not Flutter completion. **Estimate:** native 5–9h, Flutter 6–12h, desktop 5–9h.
- **User value:** the business workflow traverses actual promised platforms.
- **Acceptance:** native and Flutter independently select supported files, show byte progress and failures, explicitly export complete manifest, survive broker loss without claiming restored work; Flutter disposal reclaims only its session. macOS JVM verifier checks manifest against separately supplied directory with same negative corpus. Python's passing vectors do not close these tickets.
- **Verification/evidence:** separately compiled package/host receipts, real operations and parity vectors, altered/missing attachment scenario on each supported profile. **Risks:** UI permission/URI lifetime and cross-platform names. **Requirements:** R02, R03, R07, R15, R19.

### FP10-07 — Reconcile estimates, detailed issues and actual Projects state

- **Parent/type/phase/priority:** planning governance; documentation/integration; expand; P0.
- **Owner:** root/coordinating maintainer. **Depends on:** frozen child-ticket set; independent of reference implementation except its evidence status. **Estimate:** 3–6h.
- **User value:** the board is an actionable delivery plan rather than duplicate umbrella promises.

Dependencies form a DAG; desktop/schema/security work is not needlessly blocked on Flutter. Roll up child ranges once; old 40/120/240h figures are explicitly superseded or narrowed. All intended issues appear on one verified actual GitHub Project with URL, correct item links/status and review revision. Umbrella issue closure requires its actual children/evidence, not publication of a ticket.
- **Verification/evidence:** local ticket validator, review findings and dispositions, remote issue readback, Project item-count/status check. Do not claim board created based only on a Markdown table or attempted API mutation. If access remains blocked, state exact missing capability once and finish independent work. **Risks:** fake Done states, duplicate tickets, dangling dependencies and double-counted estimates. **Requirements:** R01, R10, R11, R18 (communication artifact only).

## Primary sources and consequences

- [Python JSON documentation](https://docs.python.org/3/library/json.html): warns that untrusted JSON can consume excessive CPU/memory; bound manifest bytes before parsing and explicitly validate structure.
- [Python filesystem APIs](https://docs.python.org/3/library/os.html): descriptor-relative operations, file metadata and platform-dependent support inform the secure-opening strategy. Pin the executed interpreter/host; do not assume identical capabilities everywhere.
- [Python pathlib documentation](https://docs.python.org/3/library/pathlib.html): path objects and resolution are useful normalization tools, not a substitute for securing subsequent file opens against concurrent change.
- [Android document access](https://developer.android.com/training/data-storage/shared/documents-files): the user-selected provider model includes local and cloud-backed storage; provider selection and grants are explicit workflow dependencies.
- [ParcelFileDescriptor reference](https://developer.android.com/reference/android/os/ParcelFileDescriptor): descriptor transport, closure and duplication must be designed and tested, not inferred from a filename.

Sources checked 2026-10-30. All work estimates and acceptance contracts above are proposals, not source-provided performance guarantees.
