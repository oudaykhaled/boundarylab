## Selection rubric

The coordinator applied the same rubric to four coherent strategies. Scores are explicit subjective planning judgments; they are neither measured results nor a vote. System-depth points for a platform strategy assume its platform gate actually completes; no such completion is currently claimed.

| Strategy | Relevance /30 | System depth /25 | Auditability /20 | Feasibility /15 | Clarity /10 | Total |
|---|---:|---:|---:|---:|---:|---:|
| App broker, native/Flutter and PC; no platform track | 28 | 18 | 19 | 13 | 9 | 87 |
| AOSP-first snapshot framework | 28 | 24 | 18 | 6 | 9 | 85 |
| Broad iOS/Android/Rust/XPC framework | 27 | 20 | 18 | 8 | 8 | 81 |
| **Staged broker + PC + gated AOSP service** | **28** | **23** | **19** | **11** | **9** | **90** |

The staged design earns early reproducible evidence without hiding the platform gap. The first two gates can run with ordinary application tooling and an existing PC host. The third requires a suitable Linux builder and booted custom image before claiming OS integration. Its main weakness is cumulative scope: 240h is a cap with real risk, not a promise. If resources fail, the honest result is a useful smaller framework plus an open platform gap.

## Deliberate choices

Choose one volatile deterministic operation rather than durable workflows. Broker loss is observable and manageable, and the project avoids a database/network recovery system unrelated to its main middleware question. This still supports meaningful architecture, reliability and compatibility experiments.

Choose Kotlin/JVM for the baseline policy core and desktop host. Add no C++ or Rust merely for appearance. The AOSP native service later provides a reason for native platform code, with its own learning allowance and semantic conformance tests.

Choose macOS CLI as the first PC implementation. The surrounding workspace already has a Mac host and mobile tool executables; actual build/socket readiness is still a G0 test. A macOS CLI in a separate process is PC software. A Flutter desktop GUI is optional, and a mobile emulator alone would be insufficient. AOSP needs separate Linux resources regardless of this choice.

Choose polling first. It provides queryable authoritative state and avoids unbounded callbacks; polling latency/energy/IPC cost is explicitly measured rather than ignored. A future callback design needs evidence that its complexity pays for itself.

## What would change this decision

- If the role is confirmed to require privileged Android framework work immediately, prioritize the AOSP feasibility/service gate before spending on desktop polish; preserve honest platform prerequisites.
- If no physical phone is available, execute correctness on a named emulator and leave physical performance unverified.
- If Flutter or the desktop adapter cannot build reproducibly, keep that requirement open and reduce scope rather than silently passing its gate.
- If the baseline demonstrates that isolation offers no consumer value, publish the negative finding and simplify the product instead of adding unsupported features.
- If real external contributors participate, record their actual contribution with consent. Their absence does not become fabricated collaboration.

No outreach, application submission, cloud spending, device flashing, product deployment or package-registry release is part of this planning task. The public GitHub repository and planned issues are the authorized deliverable.
