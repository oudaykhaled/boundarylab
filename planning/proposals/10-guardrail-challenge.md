# BoundaryLab: auditable cross-ecosystem middleware with an Android platform track

Independent proposal 10 — skeptical architecture, truthful evidence, security and feasibility. Prepared 2026-10-30. This document proposes work; no implementation, benchmark result, collaboration or commercial deployment is asserted.

## Recommended project and why

Build **BoundaryLab**, a small local capability broker that serves native Android and Flutter clients, with a Linux PC adapter and an optional, explicitly separate AOSP platform-service implementation. Its one useful workload is issuing and observing bounded synthetic work sessions: submit a deterministic checksum job, receive progress, cancel it, and recover from broker death. Payloads contain generated bytes rather than personal data. This workload exposes IPC, process identity, lifecycle, queues, cancellation, memory ownership and API evolution without concealing the engineering inside a large product UI.

The architectural question is whether several application ecosystems can consume one dependable capability while preserving each operating system's security and lifecycle semantics. A capability is a versioned contract, not a promise that Android and Linux behave identically. The demonstration should foreground a failed client, a denied caller and an incompatible protocol before showing a pleasant screen.

This is a stronger match for the advertised [Principal Architect role](https://nl.linkedin.com/jobs/view/principal-architect-%E2%80%94-os-middleware-system-frameworks-at-sparagus-4476561682) than another business application. It supplies inspectable architecture and system-facing evidence. It cannot, by itself, satisfy requirements about professional history, education, actual commercial delivery or external partnerships. The end client remains unnamed.

## Two alternatives rejected

1. **A Flutter super-app shell with plugins.** Cheap and attractive, but plugin calls and shared navigation mostly prove application integration. They provide little pressure on process isolation, authorization, service lifecycle or platform implementation. Flutter channels are an appropriate adapter inside BoundaryLab, not its central achievement.
2. **A new cross-platform OS abstraction layer covering Android, iOS, Fuchsia and desktop.** The claimed breadth would outrun credible implementation and testing in 240 hours. Different privilege and lifecycle models would become stubs or misleading uniform APIs. Prefer one deep Android track and one honest PC port; assess other platforms in decision records.

## Architecture and the real OS boundary

The contract contains `GetCapabilities`, `Submit`, `Observe`, `Cancel` and `GetStatus`. Jobs have bounded input, a caller-owned identifier, deadline, monotonically increasing event sequence and terminal state. Define admission, duplicate submission, cancellation races and service-restart semantics before designing screens. Version 1 does not persist jobs: a restart changes the broker epoch and prior sessions become explicitly lost, never silently successful.

Three separately named implementations prevent layer confusion:

- **Android application-service baseline:** a dedicated broker APK exposes AIDL to separately installed native Kotlin and Flutter client APKs. Binding is explicit. A signature permission and caller identity checks restrict access to demonstration clients. Flutter calls Kotlin through a platform channel; Kotlin calls Binder. This crosses an actual process boundary using OS IPC, but the broker remains an application-level service subject to Android application lifecycle policy. [Android AIDL documentation](https://developer.android.com/develop/background-work/services/aidl) explains the IPC and threading contract; [Flutter platform channels](https://docs.flutter.dev/platform-integration/platform-channels) describe the adapter boundary.
- **Linux PC adapter:** a per-user daemon exposes the same semantic operations over a local Unix-domain socket to a Flutter desktop client and command-line conformance client. Its private socket location, OS peer-credential check, message bounds and caller ownership are part of acceptance, not assumed from localhost. Use a small Kotlin/JVM daemon initially to avoid adding a language solely for prestige. Budget and measure its runtime overhead honestly. Linux is the claimed PC platform; Windows and macOS remain unsupported.
- **AOSP platform track:** integrate a minimal native C++ Binder broker into a pinned AOSP test image, with build definitions, init lifecycle and narrowly scoped SELinux rules. A dedicated process avoids adding experimental workload to `system_server`. Preserve the semantic contract but document any transport/interface differences. Use tracked Stable AIDL only where actually configured and verified; ordinary app AIDL must not be described as Stable AIDL. AOSP's [Stable AIDL specification](https://source.android.com/docs/core/architecture/aidl/stable-aidl) describes compatibility tracking and structured interfaces.

The final track demonstrates building and integrating an OS user-space service. It still does **not** implement the Binder kernel driver, a scheduler, a hardware driver or a production HAL. An image that runs only with permissive SELinux is incomplete: Android's [SELinux documentation](https://source.android.com/docs/security/features/selinux) describes enforcing policy and default denial. No public artifact should call any of these tracks kernel development.

Use a contract specification plus shared test vectors rather than force one common binary across platforms. Identical outcomes matter more than artificial source reuse. Keep UI, transport, policy and job execution separable. Record why this architecture is justified for multi-process consumers; acknowledge that a single ordinary app would usually choose an in-process library.

## Exact minimum vertical slice

On one Android device or emulator, install the broker and two independently packaged clients. The native client submits a 64 KiB generated input; the Flutter client submits its own input. Both display checksum and final status. Each client can observe and cancel only its own job. A third APK signed with a different test key must fail authorization. Cap accepted payloads at 256 KiB, queued jobs at 16 and active workers at two; larger requests and saturation receive stable errors. These are proposed limits, not measured optimal settings.

Kill the broker during execution. Both clients display service loss, reconnect only while appropriate to their active lifecycle, and show the new epoch; neither fabricates a completed result. Restart is driven by legitimate binding or the platform-track service supervisor, not a promise of an immortal app process. Include a reproducible command sequence and automated assertions for the complete flow. Linux and AOSP are later evidence, not dependencies for calling this slice complete.

## Measurable benchmark and fault plan

Record revision, OS/build, device, runtime/toolchain, compilation mode, thermal/power conditions and exact workload with every run. Use release-like clients. Android startup measurements should use [Macrobenchmark-supported startup analysis](https://developer.android.com/topic/performance/appstartup/analysis-optimization), while service readiness gets separate monotonic timing instrumentation. Do not combine phone and emulator numbers into one performance score.

Initial experiment: five warmups followed by 30 repetitions for startup/readiness; report median, p95, range and all raw samples. Increase repetitions before drawing tail-latency conclusions. Sweep 1, 2, 4 and 8 clients, with 1 KiB, 64 KiB and 256 KiB payloads. Separate channel, Binder/socket, queue wait and execution time. Report throughput, rejection count, CPU, process memory and cancellation-to-quiescence delay. A comparable in-process execution mode estimates transport overhead but does not provide equivalent isolation.

Proposed engineering gates are zero cross-caller access in the test corpus, queue never above its configured cap, terminal-state consistency, no client main-thread wait on job execution, and no unbounded growth during a 30-minute load run. Establish numerical latency and memory regression budgets only after a stable baseline; a tentative 10% change should trigger investigation rather than an automatically claimed regression on noisy hardware. Deterministic functional failures block merging; device performance gates require controlled runners and repeated confirmation.

Inject broker and client death, oversized and malformed messages, invalid version, queue saturation, cancellation/completion race and stalled observers. Verify ownership at submit/read/cancel boundaries. Redact process logs to generated IDs and omit raw payloads. A failing required scenario is a top-level gap, never hidden behind an alternative demo path.

## Open-source and GitHub packaging

Propose a single repository with `contracts`, `android`, `flutter_client`, `linux`, `aosp`, `tests`, `benchmarks`, `docs/adr` and `evidence`. The README opens with delivered versus planned capabilities and the OS-layer distinction. Until implementation exists, publish it as a **project plan**, with unchecked milestones and no fake build badges or screenshots.

Include an explicit license for original work, third-party notices, contribution guide, security reporting instructions, threat model and evidence index. Pin dependencies and test-image manifests when implemented. Large images belong in a release distribution strategy after license and hosting review, not casually in Git history. Public materials must exclude personal contacts, private resumes, employer code, credentials and workstation paths. A public clone reproduction is the packaging acceptance test; no secret local setup step may be required. CI must fail on contract drift and required test failures rather than merely upload reports.

0:00–0:40: show the layer diagram and current evidence scope. 0:40–1:40: submit jobs from native and Flutter clients to the same process, displaying process IDs and trace markers. 1:40–2:30: deny an unauthorized caller and reject a saturated queue. 2:30–3:20: kill the broker, show honest session loss and reconnect. 3:20–4:10: replay the Linux semantic test and explain its lifecycle differences. 4:10–5:00: show one measured tradeoff and, only if completed, the AOSP service registration and enforcing-policy test. If a track is unfinished, show its explicitly labeled design gap instead of prerecorded pretend success.

## Major risks and recommendation score

The hardest risk is an attractive app demo being mistaken for OS middleware expertise. The remedy is layer-specific evidence and a separately gated platform implementation. Next are build-host availability, AIDL/threading bugs, misleading cross-device comparisons, unjustified always-running behavior, and deadline pressure encouraging superficial breadth. A small, correctly bounded broker is preferable to an ambitious universal framework with untested paths.
