# BridgeQueue: independent delivery and reuse proposal

Planning date: 2026-10-30. All milestones, budgets and acceptance thresholds below are proposed, not achieved. This proposal targets the supplied Sparagus Principal Architect requirements; it does not infer the unnamed client or promise hiring outcomes.

## Recommended project and rationale

Build **BridgeQueue**, a bounded, cancellable local work broker with Android Binder transport, native Kotlin and Flutter clients, and a desktop JVM host. Its deliberately small workload hashes deterministic generated byte streams. Real product analogues include indexing, import and media processing pipelines, but this project processes synthetic data only. Work generation occurs inside the worker; IPC carries small descriptors and progress snapshots, not large byte arrays.

The architectural story is resource control across application boundaries: two applications request work, one broker enforces capacity and ownership, slow clients cannot consume unlimited memory, and clients recover explicitly after broker death. This exposes IPC threading, lifecycle, permissions, backpressure, cancellation and compatibility in one understandable scenario. Android expertise is the strongest known starting point; Flutter supplies a separate application ecosystem without a second mobile OS commitment.

Recommend the **120-hour track as the initial commitment**, with a 40-hour stop gate. The 240-hour track is justified only after runnable evidence proves that another platform or optimization answers a concrete reviewer question. Time estimates assume one experienced Android engineer, focused hours, working hardware, and modest Flutter familiarity; learning and broken toolchains consume the same budget.

Two alternatives rejected:

1. **AOSP fork with a new system-server service.** It offers stronger platform implementation evidence, but image builds, privileged integration and device flashing can consume the entire initial budget. A credible custom image plus maintenance story exceeds this proposal's predictable critical path. Reconsider only if the recruiter confirms privileged framework implementation is essential and suitable hardware already exists.
2. **Five-platform universal SDK with a polished dashboard.** Broad adapters dilute time spent diagnosing actual failures. Compilation badges do not establish lifecycle correctness or device compatibility. Begin with Android and one PC operating system; require evidence before adding iOS, ChromeOS or Fuchsia.

## Architecture and actual OS boundary

Proposed components:

- `broker-core`: pure Kotlin/JVM admission, bounded queue, job state machine, cancellation and deterministic worker; no Android imports.
- `android-service`: separate installed broker package exposing an AIDL bound service, a signature permission, explicit caller identity checks and per-caller quotas.
- `android-client`: small Compose application and SDK wrapper; never blocks the UI thread waiting for IPC.
- `flutter-client`: Dart interface with Android Kotlin platform-channel implementation that binds to the same service.
- `desktop-host` and `desktop-cli`: same core, separate JVM processes using loopback framed messages, bounded frame sizes and a per-run capability token. No remote listening. Desktop security semantics are explicitly weaker/different than Android UID enforcement.
- `conformance` and `evidence`: semantic fixtures, fault scripts, release metadata and raw results.

Android AIDL supplies cross-process marshalling and has threading semantics the service must handle [S1]. Flutter channels connect Dart to platform code; the Android adapter then crosses Binder into the broker [S2]. That is two distinct boundaries, visible in trace events. A bound service has lifecycle constraints and must not be represented as an always-running system daemon [S3]. Custom signature permissions restrict the demo applications to the intended signing trust domain [S4]. Separately signed negative-test clients must fail to bind.

The owned work is user-space middleware on OS facilities. It does not implement Binder, a kernel driver, Android system_server or an operating-system scheduler. The state machine must distinguish service reconnection from job restoration: first release jobs are volatile and become `lost` after process death. Never imply durable recovery or exactly-once execution. A new broker epoch prevents stale job handles from being mistaken for current work.

## Exact minimum vertical slice

The 40-hour slice comprises one native client APK, one broker APK and a differently signed denial-test APK. The client submits a 32 MiB deterministic streaming hash job using a descriptor, displays state by polling, cancels it, then observes `lost` after a deliberate broker crash and reconnect. Use one worker, queue capacity 16, fixed buffer size, maximum descriptor size and stable error values: `busy`, `invalid`, `unauthorized`, `cancelled`, `lost`. Capture a raw trace that identifies client PID, service PID, worker dispatch and completion.

Acceptance: digest equals an independent reference; queue saturation returns `busy`; cancellation leaves no running worker after the documented timeout; broker death produces no false success; denial client cannot access the service; UI stays responsive during worker activity. Implement process-crash injection only in a clearly identified test build and demonstrate clean release-build behavior separately. No desktop, Flutter or durability is required for this slice.

## Measurement and fault plan

Publish a machine-readable manifest with commit, build mode, tool versions, OS/API version, hardware model, power/thermal conditions and test parameters, excluding serial numbers and private paths. Keep emulator correctness runs separate from physical-device performance measurements. Android Macrobenchmark supports startup measurement [S5]; Perfetto supports trace-based inspection [S6].

Measure three costs independently: no-work round trip, admission-to-start queue delay, and end-to-end hash completion. Use 100 warmups then 1,000 measured no-work requests per configuration; report sample count, median and p95. Run at least 20 cold launches and 20 warm launches, explicitly identifying service residency and compilation conditions. Avoid precise p99 claims from small samples. Capture core worker baseline so framework overhead is not confused with work duration.

Run payloads 1/32/128 MiB, clients 1/2/4 and worker limits 1/2; reduce the matrix if device thermal drift invalidates it. Keep request metadata below a proposed 4 KiB limit, queue at 16 and active worker allocation bounded by configuration. Polling starts at 100 ms for the demonstration, with overhead recorded. Observe PSS for every participating process before, during and five minutes after 100 job/cancel cycles. Provisional acceptance: no monotonic retained-job growth, no admission beyond the cap and no UI-thread IPC waits. Numerical latency and PSS regression budgets are calibrated from three repeated baseline sessions before being used as gates; an illustrative 10% regression requires repeat confirmation rather than automatic claims of significance.

Faults: kill broker during work; disconnect client; submit duplicate IDs; malformed/oversized descriptors; queue flood; stale broker epoch; deadline expiry; cancellation racing completion; unauthorized caller; old-client/new-service handshake. Specify allowed outcomes for each race. Duplicate ID handling is bounded to the current epoch, never exactly-once across crashes. At 240h add two-hour soak, broader client pressure and delayed responses. Archive failures as well as successes.

The critical path is A → B → C → D → E/F → G → H; one engineer performs E and F sequentially. **40h:** A–D, nominal 40; ranges total 31–52. **120h:** A–H, nominal 120; ranges total 91–154. Reserve the last 12 hours of each timebox for evidence and packaging by reducing preceding scope. If 120h estimates trend toward 154, defer desktop delivery explicitly and publish a partially covered requirement matrix rather than falsely marking R03 complete.

**240h total:** add 24h Flutter desktop client on the already tested OS, 24h second Android device/API and two-hour soak, 28h measured optimization and regression work, 20h independent reproduction and genuine review handling if available, and 24h contingency/release work. Extension ranges are roughly 90–150h; new scope remains optional until each preceding gate passes. Desktop Flutter support exists for Windows, macOS and Linux, but actual host toolchain readiness decides the single target [S7].

Stop gates: at hour 8, a clean sample must build and the device must run it; otherwise publish blocker and adjust target. At hour 24, a real cross-process request and permission denial must work; if not, freeze adapters and fix that boundary. At hour 40, no additional ecosystems until crash semantics are demonstrable. At hour 80, stop adapter work if both cannot build reproducibly; prioritize trustworthy Android evidence. At hour 108, freeze features. At hour 200, admit no new platforms.

NOT proven by 40h: Flutter, PC support, sustained load, optimization outcome, external collaboration. NOT proven by 120h: multi-OS desktop UI, broad hardware compatibility, durable execution, production deployment. NOT proven by 240h: kernel implementation, commercial operation, unrestricted ecosystem support, education, European tenure or partner relationships. The last five categories require independent evidence regardless of budget.

## Reuse, unknowns and highest evidence per hour

A targeted local README inspection identified TransferFlow's useful public patterns: synthetic fixtures, explicit recovery states, a short reviewer guide and revision-specific verification. Its README links the public repository [S8]; inspect license and provenance before any future code reuse. Reuse documentation structure and ideas first; its banking domain, Room ledger and payment semantics are unnecessary here. A second inspected README identified itself as private: exclude its code and claims from public reuse. No source copying is proposed.

Unknowns to resolve in A: physical Android device availability; a second device for later testing; JDK/Gradle/SDK compatibility; Flutter/Dart installation and familiarity; desktop OS build prerequisites; signing setup; usable profiling permissions; CI runner availability and cost. Do not assume the surrounding machine's toolchain is ready. C++/Rust are deliberately absent from the critical path. A hosted Linux runner can prove builds, not the performance of the owner's phone or desktop.

Highest evidence per hour is a real process-death trace with a correct client state, followed by unauthorized-client denial, bounded overload behavior and two ecosystems using one broker. Lowest return is elaborate UI, Kubernetes, a cloud backend, installing every mobile toolchain or a custom serialization framework.

## Open-source packaging and five-minute demo

Prepare a single repository with a license selected after dependency/provenance review, root quickstart, architecture diagram, requirement matrix, ADRs, versioned contract, CONTRIBUTING, security-reporting guidance and a local board. The owner alone updates board status: planned, implemented, reviewed, released and device-verified are separate facts. CI builds and tests pinned dependencies; physical benchmark uploads carry manifests and checksums. Release includes source tag, Android artifacts, desktop invocation, raw measurements and an uncut demonstration. Publishing remains an explicitly scoped parent workflow; this proposal creates no remote resources.

Demo: 0:00 explain the boundary diagram and limits; 0:40 submit from native and Flutter clients; 1:30 overload queue and show a predictable busy response; 2:10 crash broker, show `lost`, reconnect and submit anew; 3:00 show desktop conformance or clearly labeled 40h omission; 3:40 open trace and one benchmark with raw data; 4:30 show version compatibility and honest requirement gaps. Keep a verified recording available if hardware fails, clearly identifying its revision.

Major risks are toolchain recovery consuming scope, Flutter learning, overstating user-space work, noisy benchmarks, and marketing readiness as completed collaboration. Reduce breadth before reducing correctness evidence.
