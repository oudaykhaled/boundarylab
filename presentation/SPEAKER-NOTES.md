# BoundaryLab speaker notes

Eight scenes. The browser animation illustrates a proposed design; it is not recorded product execution.

## 1. Make local work predictable

“Applications that run work in another process need more than a submit button. They need to decide who owns a job, how much work is allowed, how cancellation behaves, and what users see when that process disappears. BoundaryLab proposes a small, inspectable contract for those decisions. The aim is reusable integration machinery. Today this is a project plan; the animation explains what we intend to build and test.”

## 2. One broker, one contract

“The demonstration operation computes a checksum over generated bytes. That keeps the example deterministic and avoids private documents or arbitrary code execution. Its value is not the checksum feature itself. The reusable pieces are the SDK, admission rules, lifecycle contract, and conformance tests. A separate consumer will need to use them before we claim integration value. For a single application, an in-process library may still be the simpler choice.”

## 3. Two ecosystems, real boundaries

“The first Android implementation uses three independent packages: a native client, a Flutter client, and a broker. Flutter reaches native code through its plugin; both clients use the Kotlin SDK and cross Binder into the broker process. Policy lives in the bounded core, not the screens. This proves application-level middleware and real IPC when implemented. It does not prove OS framework modification. That stronger platform boundary belongs to a later, conditional AOSP track.”

## 4. Identity before admission

“The broker must trust transport identity, not a name supplied in a request. Android captures the Binder caller before asynchronous work and checks the server-issued session and job owner. The demonstration restricts access to the same publisher through a signature permission. Admission then enforces explicit resource caps. The initial proposal uses one worker, sixteen queued jobs globally, and four outstanding jobs per session. These are design limits awaiting implementation and adversarial tests.”

## 5. Reconnect is not recovery

“This is the most important failure promise. Jobs are volatile. If the broker dies, accepted work does not survive, and a client may not know whether an operation completed before the connection broke. Rebinding restores access to a new broker epoch; it does not restore the old job. Old handles become invalid. The user or caller explicitly resubmits to start new work. There is no persistent recovery, automatic replay, or exactly-once claim.”

## 6. Measure the tradeoff

“Process isolation has costs, so faster is not an assumption. The plan compares equivalent deterministic work under declared build and device conditions. It separates process startup, the first UI frame, and middleware readiness, then examines latency distributions, memory, cancellation and overload behavior. Each conclusion must link to raw observations and its exact environment. Failed hypotheses stay in the report. At present there are no benchmark results, and these graphics are only the proposed evidence workflow.”

## 7. Earn each gate

“The forty-hour target is the Android boundary proof, including Flutter, denial, cancellation, and honest process-loss behavior. At one hundred twenty hours, the first PC implementation is a macOS JVM host and CLI using the same core and semantic fixtures. It is not a desktop GUI or phone synchronization. The conditional two-hundred-forty-hour track adds a dedicated AOSP service and enforcing policy. It requires suitable Linux resources and a booted, tested image. Hours alone never pass a gate.”

## 8. Inspect every claim

“The intended outcome is an artifact a reviewer can inspect, not a technology checklist. Every future claim should lead to a source commit, a test or trace, an environment, and a clear limitation. Planned, implemented, and independently reproduced are different states. Today the public artifact is the plan. Even a successful AOSP track would not establish kernel implementation, commercial adoption, or professional history. The next useful step is to execute the first boundary gate and publish what actually happened.”
