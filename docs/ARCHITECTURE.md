# Architecture and behavioral contract

Design record: this document preserves the initial component and behavior decisions. Current implementation and verified scope are recorded in [execution status](../planning/EXECUTION-STATUS.md); the [native AOSP layer diagram](AOSP-LAYERS.md) identifies the actual platform versus user-space integration. The [revised plan](PLAN-V2.md) defines delivery gates. The [FieldPack contract](FIELDPACK.md) supersedes the file, byte-budget and lifecycle details below where specified.

## Product and boundary

BoundaryLab gives several applications a local execution capability with explicit resource and failure semantics. The controlled benchmark hashes generated bytes in bounded chunks; FieldPack adds bounded regular-file hashing under the separate [file profile](FIELDPACK.md). IPC carries a seed, byte-count and operation identifier rather than a document or huge byte array. A known digest provides an independent correctness oracle. Real files are opened under explicit user authorization and the bounded supported-input profile. No network service, arbitrary script execution or persistent queue is needed.

The value hypothesis is that a small SDK plus conformance suite reduces the work required to integrate process-isolated, cancellable operations. Test this with a separately built consumer before claiming utility. A single-app implementation may reasonably prefer an in-process library; isolation has a measurable cost.

| Proposed component | Owns | Does not own |
|---|---|---|
| `core/` Kotlin/JVM | Validation, admission, quotas, state transitions, bounded scheduling and deterministic work | Android contexts, UI, IPC identity, sockets |
| `android/broker/` | Explicit bound service, AIDL boundary, caller capture and authorization, lifecycle | UI or indefinite background availability |
| `sdk/kotlin/` | Worker-thread calls, connection generation, typed results and foreground-demand binding | Hiding unknown outcomes or replaying work automatically |
| `sdk/flutter/` | Dart facade, native plugin and engine-scoped lifetime | Implementing Binder or the OS scheduler |
| `examples/android-native/`, `examples/flutter/` | Small submit/status/cancel screens | Middleware policy |
| `desktop/host/`, `desktop/cli/` | macOS per-user JVM host, framed local socket, transport identity and limits | Android-equivalent UID or lifecycle semantics |
| `conformance/`, `benchmarks/` | Golden vectors, old-consumer fixtures, fault orchestration and observations | Claims beyond the tested environment |
| `aosp/` | Conditional image-integrated service, build/boot/security and platform-facing facade | A new kernel, driver, HAL or production certification |

Android and macOS share the pure JVM core, not a process or job store. There is no phone-to-PC communication or synchronization. Cross-platform compatibility means matching observable semantics on each host.

## Android application profile

Install three independent packages: broker, native client and Flutter client. Explicit binding and a project signature permission restrict the demonstration trust domain. Generate local demonstration signing material outside source. A differently signed negative client is an additional test artifact. Do not publish a reusable private signing key.

Authorize every operation using Binder caller UID/user captured before asynchronous dispatch. Derive ownership from that identity and a server-issued session; never trust a submitted package string. A guessed job ID must not enable status or cancellation across owners. Validate sizes and versions before allocating work. No cross-user access is supported. The signature-only profile supports separately built same-publisher consumers; it does not promise arbitrary third-party onboarding.

Binder ingress performs bounded admission, then returns; hashing runs on owned workers. Remote AIDL calls can arrive concurrently, so serialize state changes deliberately. Keep blocking IPC off client UI threads. Start with bounded polling rather than callbacks; this reduces callback reentrancy and slow-listener complexity. The [Android AIDL guide](https://developer.android.com/develop/background-work/services/aidl) grounds those IPC/threading obligations.

A bound service follows application lifecycle policy. Visible clients own demand; the SDK stops rebinding when that demand is gone. The service is allowed to disappear. No foreground-service exemption, perpetual background worker or boot improvement is claimed. See [bound-service lifetime](https://developer.android.com/develop/background-work/services/bound-services).

## Contract v0.1

Operations: `capabilities`, `openSession`, `submit`, `status`, `cancel`, `closeSession`. The handshake returns protocol major/minor, broker epoch and advertised limits. The server issues an opaque owner-bound session. On Android, openSession registers a client-owned Binder token and death recipient; a polling-only client still needs this token for real client-death cleanup. On desktop, the session is bound to the connection lifetime and its deadline. A submit descriptor contains operation, deterministic seed, total byte count, relative deadline and request ID. Identity is supplied by the transport, not this descriptor.

Proposed starting caps: descriptors 4 KiB; total job work 128 MiB; fixed work buffer 64 KiB; one worker; 16 queued jobs globally; four outstanding jobs per session; 16 sessions; at most 64 retained terminal results with a 60-second TTL. Cap encoded responses and total retained bytes as well as entry counts. Reject with `BUSY` or `INVALID` before exceeding a cap. The exact retained-byte ceiling is 1 MiB in the revised contract; implementation must enforce it. This accounts for metadata/result retention, excluding fixed runtime overhead and the work buffer.

States: `ACCEPTED → RUNNING`, with `RUNNING → SUCCEEDED` and both `ACCEPTED` and `RUNNING` allowed to reach `FAILED` or `CANCELLED`. Cancellation while queued removes the job before execution. Deadline expiry while queued commits `FAILED(DEADLINE_EXCEEDED)` and never starts work; expiry during execution requests cooperative stop and commits that failure only if completion did not already win. The state owner serializes these races, and terminal states never overwrite one another. Requests observed across broker loss become `LOST/UNKNOWN` in the client. A new broker epoch invalidates old handles. There is no persistence and no recovery of previously accepted work after broker death. Rebinding restores transport access; explicit resubmission starts a new job. No exactly-once delivery or durable intent is claimed.

Duplicate request IDs have bounded deduplication only inside one owner/session/epoch and retention window. A retained ID with different input returns `CONFLICT`; one outside retention is not promised deduplication. Expired or evicted results return an explicit `EXPIRED/UNKNOWN` response; bounded retention is not a durable completion guarantee. A submit timeout can mean the server accepted work: query the original session/request before deciding what to do. A client must never turn a timeout into success.

Cancellation is cooperative. Running cancellation records intent until a serialized worker terminal commit; a blocked read is not forcibly interrupted. If completion commits first, return the actual completed state; if cancellation commits first, no later success may overwrite it. A caller timeout only stops waiting unless the SDK also sends cancellation. Queryable state remains authoritative. A job deadline bounds admitted work; a non-cooperative worker hang is reported and may require broker-process restart in a test environment, not unsafe thread termination.

Use bounded round-robin admission across active sessions so one flood cannot indefinitely starve another caller. Test actual fairness under load before claiming it. Closing or losing a session cancels its work and reclaims retained records according to the contract.

## Client and Flutter lifetime

Connection states: `UNBOUND → BINDING → READY → RECOVERING`, with terminal `DENIED`, `INCOMPATIBLE` and explicit unavailable/retry state. Merge service disconnection and Binder death into one generation-aware transition; preserve distinct `onBindingDied`/null-binding handling. A capped retry budget applies only while foreground demand exists. Drop observations from old generations.

Each Flutter engine owns a plugin instance, connection/session and disposal path. Do not retain an Activity or use global callback state. Configuration recreation and engine destruction are different events. Method-handler work is scheduled off the platform UI thread where appropriate; callbacks follow documented platform threading rules. Test native execution, cancellation, timeout cleanup, engine teardown and a second engine separately. [Flutter channels](https://docs.flutter.dev/platform-integration/platform-channels) explain the bridge mechanism; generation and cancellation semantics are BoundaryLab's own contract.

## PC profile

The first PC target is macOS with a supported JDK ([Java Unix-domain socket API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/net/UnixDomainSocketAddress.html)) and two actual JVM processes: host and CLI. The pure Kotlin core runs in the host; the CLI uses bounded length-prefixed frames over a Unix-domain socket. A private owner-only runtime directory and restrictive socket permissions constrain access to the same OS user. Validate ownership/path before connecting, reject malformed frames, apply read/write deadlines and clean shutdown. Peer-credential validation is added only after the chosen JDK/macOS combination is proven to support it; without it, the documented trust boundary is the private directory and same-user model. Same-user hostile processes are outside this baseline trust guarantee.

Do not expose a network listener or publish a runtime token. Verify selected JDK socket support in the initial spike; if unavailable, keep R03 open until an explicitly redesigned transport passes equivalent tests. This is a real desktop implementation, not an Android emulator relabeled as a PC port. No desktop GUI or Linux support is included in the G2 gate. A future Flutter desktop adapter is optional after the required evidence, not a hidden prerequisite.

## Conditional AOSP platform profile

For stronger system-software evidence, implement the same narrow capability as a dedicated native Binder service built into one pinned AOSP image. A dedicated process contains experimental work outside `system_server`. Add build definitions, init supervision with bounded crash-loop behavior, service registration, tracked structured AIDL, a narrow platform-built client/manager facade, permission enforcement and least-privilege SELinux policy. Reuse semantic vectors; the native implementation need not share the JVM binary. Keep interfaces internal to the test system image; no vendor interface or VINTF stability claim is needed.

Compile the test client/facade against the deliberate custom platform API. Ordinary downloadable applications continue using the stock-Android broker; do not reflect into hidden service-manager APIs. Verify authorized and unauthorized paths, service restart/epoch behavior, boot registration and a compatible interface change on a booted image with SELinux enforcing. A source patch alone is incomplete.

The [AOSP backend restrictions](https://source.android.com/docs/core/architecture/aidl/aidl-backends) and [Stable AIDL rules](https://source.android.com/docs/core/architecture/aidl/stable-aidl) distinguish this profile from Gradle app AIDL. The exact integration API/build target is frozen after the image feasibility spike. Retain an ADR comparing a dedicated daemon with `system_server` placement and explain blast radius, startup order, isolation and maintenance costs.

This track needs suitable Linux build and virtualization resources. Current [AOSP host guidance](https://source.android.com/docs/setup/start/requirements) calls for substantial RAM/disk and does not support current OS development on macOS. [Cuttlefish](https://source.android.com/docs/devices/cuttlefish) supplies a platform-development target; it does not establish physical-phone performance. No cloud purchase, device flashing or service deployment is authorized by this plan.

## Compatibility and exclusions

API shape, transport encoding, behavior, packaging and lifecycle are separate compatibility axes. Keep previously compiled client fixtures, additive version changes and explicit rejection of unsupported major versions. Declaring a version field cannot fix an incompatible AIDL layout. Pin the exact Android/API/JDK/Flutter versions at kickoff after testing available targets; do not advertise a version range before executing its endpoints.

Out of scope: React Native, iOS, Fuchsia, ChromeOS, Windows, arbitrary runtime plugins, arbitrary file/provider support outside the FieldPack profile, cloud services, distributed scheduling, durable execution, cross-device sync and OS kernel work. Dated assessments of alternatives satisfy a research artifact only; they are not implementation claims.
